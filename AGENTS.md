# aditor-scorecard - agent notes

Project-intrinsic knowledge that should travel with the code: what is safety-critical, how the tests work, and the sharp edges.

`aditor-scorecard` is a client-only Vite + React 19 SPA (plain JSX, no TypeScript).
It is a read-only internal dashboard served at https://score.aditor.ai with a **single view**: the **Scorecard** - a weekly/quarterly KPI grid read directly from Teable in the browser and grouped into five department cards (Marketing, Sales, Customer Success, People, Automation).

> The **Brands/Kingdom** ("castles") tab was **removed in 2026-07** (decided 2026-07-02). It was the only mutating/outbound surface (two `gen.aditor.ai` calls) and is gone: its components (`Castle*`, `Editor*`, `BrandActions`), `editorSprite` util, `castle-grid.css`, and `public/{castles,editors}/` assets were deleted, along with its two specs. The **dashboard** now has **no** money/auth/mutation/outbound surface.

> **IG metrics collector removed (2026-07-07).** A weekly Cloudflare Worker at `collector/` used to write two Instagram marketing metrics (`reach`, `hotDms`) into the Teable weekly row. It was **decommissioned on 2026-07-07**: its `collector/` code and its CI deploy (`.github/workflows/deploy.yml`) were deleted from this repo (recoverable from git history), and the deployed Worker was torn down separately. IG metric collection is being **rebuilt as n8n workflows** outside this repo. The dashboard is **unchanged** - it still renders `reach`/`hotDms` (and every other row) read-only from the Teable feed; only the writer of those two fields moved out. With the collector gone the repo again has **no** money/auth/mutation/outbound surface.

## Test surface

The **dashboard** is entirely a read-only render of the Teable feed, so the SPA itself has **no T1 items** (nothing in the browser touches money movement, auth, data mutation, or outbound sends); its test is the build only. With the `collector/` Worker removed (2026-07-07), the repo no longer has any mutating/outbound surface or T1 items at all. The dashboard's one external boundary is the Teable read.

- **Teable read** - `dashboard/src/hooks/useScorecard.js` (`GET /api/table/{id}/record`, url built at `:96`). Read-only fetch + pure mapping. Defensive by design: a field absent in Teable maps to `null` (`toNum`) and renders as a neutral placeholder ("—"), never a crash. The bundled read-token is a security note (below), not a test gate.
- **All of `App.jsx`** - pure display + aggregation of already-read data (`filterByMonth`, `aggregateToMonths`, `addTotalColumn`, `getStatus`, `fmt`, ISO-week slotting). Date math is bug-prone but display-only, so it is not a gate; since the browser suite was removed (2026-08-20) a rollup or date-math bug is caught by reading the diff and the deployed page, not by CI.
- **Money display** - `mrr`, `cpl`, `closeRate`, `costPerCall` are numbers rendered from Teable. No payment provider, no money movement, no write. Not sensitive.
- No email / Slack / CRM / SMS / webhook-send exists at runtime anywhere in the repo. (Slack is called **only at build time** to bake owner avatars - see below.)

### Department + metric structure (`App.jsx`)

- `METRICS` (key → `{name, icon, unit, dir, green, yellow, agg, desc, neutral?}`), `DRI` (dept id → owner `{name, initials, color, img}`), `DEPARTMENTS` (ordered list; the 5th, Automation, carries `centered: true`).
- Owners: Marketing = **Tobias**, Sales = **Alan**, Customer Success = **Saskia**, People = **Tim**, Automation = **Shawn**.
- **Automation** is the 5th card, rendered centered on its own row under Customer Success via `.dept-card.dept-centered` (spans the 2-col grid, `justify-self: center`, one-column-wide; full-width at ≤1000px). Its rows (renamed/reordered 2026-07) are **Requests Done** (`automationRequests` - a done/incoming completion ratio, `frac`, colored by percent: 100% green / 50-99% yellow / <50% red), then 3 `dir:'lower'` threshold rows: **Turnaround Time** ≤3 / ≤6 days, **Critical Errors** ≤1 / ≤3 per week, **Resolve Time** ≤12 / ≤24 h.
- **Rollup semantics (`agg`, fixed 2026-08-10).** How a metric rolls into a month or Total column is decided entirely by its `agg`, and picking the wrong one is a silent display bug - the live Automation card showed "1.5 critical errors" for August because a COUNT was declared `agg: 'avg'`. The rules: `sum` for counts, `avg` for per-week averages, `last` for point-in-time levels, `frac` for done/incoming pairs (both parts sum). An `avg` metric whose weekly value is itself an average over a cohort must declare `weightBy` (the row field holding that week's cohort size) or the rollup is an unweighted mean of means that over-weights quiet weeks - `autoTurnaround` weights by `automationRequestsDone`, `autoIncident` by `autoErrorRate`. `WEIGHT_FIELDS` carries any weight field that is not itself a metric into month columns. Both rollup paths (`aggregateToMonths`, `addTotalColumn`) share `weightedAvg` / `sumOf` / `sumFrac` so month view and quarter view can never disagree again; they did, because only one of them rounded averages to whole numbers. `sumFrac` returns null (renders "—") for a month that carried no data at all, instead of a misleading "0/0". These rules used to be pinned by `tests/aggregation.spec.js`, removed 2026-08-20 - nothing enforces them now, so re-derive them by hand when you touch a rollup path.
- **Marketing metric banding (thresholds set 2026-07).** Tobias's 3 Marketing metrics are color-banded like IG Posts (they were `neutral` until thresholds were set): `reach` green ≥100k / yellow 50-100k / red <50k; `hotDms` green ≥10 / yellow 5-9 / red <5; `followers` (weekly net gain) green ≥100 / yellow 50-99 / red <50 - all `dir:'higher'`. **These are set intentionally; do not auto-adjust.** `reach` + `hotDms` are populated in Teable by the IG metrics feed (the `collector/` Worker until it was removed 2026-07-07; being rebuilt as n8n workflows) - the dashboard just renders whatever is in Teable. `reach` is the Marketing slot that used to read the paid-ads `impressions` field (rewired 2026-07). Values display in **k-notation** (`kfmt`: ≥1000 → `31.5k`, using the true value). Sum-metric TOTAL thresholds scale by the weeks that actually have data for that metric (so a just-started metric's single real week doesn't mis-band the total). That scaling applies in **both** directions since 2026-08-10: a `dir:'lower'` sum metric (Critical Errors) compared against its per-week threshold would go red on any multi-week total above 3.

### Automation metrics - corrected definitions (2026-07-06)

The Automation rows (2026-07) are **Requests Done, Turnaround Time, Critical Errors, Resolve Time** - all data-driven from Teable (dash for null). Weekly values change; render whatever is in Teable, **never fabricate**. Definitions:

- **Requests Done** (Teable `automationRequests` incoming + `automationRequestsDone` done → a `frac` done/incoming ratio, colored by completion %): automation/feature requests completed vs incoming for the week (requests come from meetings + Slack).
- **Incidents / week** (→ the count cell: Teable `criticalErrors` → `autoErrorRate` "Error Rate"): count of **deduped incidents** entering the incident pipeline that week across THREE sources - n8n **cloud** (deduped), n8n **server** (self-hosted `n8n.aditor.ai`, deduped), and **Slack**-reported incidents, warnings excluded. NOT raw n8n workflow error executions. (The earlier `34` was n8n-cloud-only and wrong; recomputed to `5` for KW27.)
- **Automation requests + Turnaround** (→ Teable `turnaroundTime` → `autoTurnaround` "Turnaround"): the automation-request pipeline pushes tasks to the kanban board; requests come from **meetings + Slack**. Backfill source: the automation Slack bot **DMs the requester** their tasks after each meeting - pull last week's from those DMs (or from the worker / kanban). Turnaround = request timing (received → delivered); if delivery timing is unavailable, populate the request COUNT and flag Turnaround.
- **Incident Resolve** (Teable `incidentResolution` → `autoIncident`): resolution TIME - **not** one of the two corrected metrics; no backfill source defined yet, so it stays dashed.
- **Access blockers to clear first:** self-hosted `n8n.aditor.ai` history API (unauthorized/blocked), and Slack read access for incident messages + the bot DMs.
- The dashboard `desc`/thresholds for these rows still encode the OLD definitions (e.g. "Error Rate" = "unblocked n8n errors, green ≤1"); revisit them when the corrected metrics are wired and real ranges are known.

## Tests

The gate is the **hermetic build**. `.no-mistakes.yaml` `commands.test` runs exactly:
```
(cd dashboard && npm ci && npm run build -- --mode test)
```
`--mode test` bakes in `dashboard/.env.test` - committed, non-secret placeholders that point the one network boundary (the Teable read) at the discard port `127.0.0.1:9`, so nothing in the gate can reach a real instance. `.env.test` must stay committed; it is what makes the build hermetic.

There is no browser suite and no unit suite. Two were removed:
- The `collector/` vitest suite went with the IG metrics collector Worker on 2026-07-07.
- The **Playwright browser suite was removed on 2026-08-20** (`dashboard/tests/`, `dashboard/playwright.config.js`, the `@playwright/test` devDependency, and the `test:e2e` script), along with the browser step in `.github/workflows/deploy-dashboard.yml`. It is recoverable from git history at the commit immediately before that removal.

So the build is the whole gate: it catches a syntax error, a bad import, a broken Tailwind/PostCSS config, or a missing asset, and nothing beyond that. There is no TypeScript, so "typecheck" is the Vite build. Display and date-math regressions are **not** covered by CI - the dashboard is a read-only render with no money movement, auth, mutation, or outbound send (see Test surface above), so those are caught by review and by looking at the deployed page.

If you reintroduce a runtime test suite, keep the two rules the old one enforced, which are properties of this app and not of Playwright:
- **Never touch production.** Fake the Teable boundary and fail closed on any non-localhost request; reverse-engineer fixtures from consumer code, never from a live call.
- **Pin the clock and the timezone** (`Europe/Berlin`). `App.jsx` / `useScorecard.js` read wall-clock in many places - current-week highlight, month/quarter defaults, the 5-min refresh interval - so an unpinned run is machine-dependent.

## Known facts / sharp edges

- **Default branch is `master`.** This repo ships straight to `master` through the no-mistakes gate with **no pull request**, and since 2026-08-20 the only automated check is the hermetic build (see Tests). Read the diff before you push; nothing downstream will catch a display regression for you.
- **The repo root is a stale build artifact that never deploys.** `dashboard/` is the source of truth (the Vite project). The repo root (`index.html`, `assets/`, `avatars/`, `CNAME` = `score.aditor.ai`) is an old committed copy of the built SPA, left over from when publishing meant running `npm run deploy` locally. CI publishes `dashboard/dist` and nothing else, so **editing the root changes nothing about what users get** - and since `npm run deploy` was deleted (2026-08-20) nothing regenerates or clears the root either. Do not test it, do not hand-edit it. (It still carries the dead `castles/` + `editors/` dirs from before the Brands removal.) Deleting the whole root bundle would be safe and is worth doing; it survives only because nobody has confirmed no bookmark depends on it.
- **Pushing to `master` IS the deploy, from any machine with push access.** That is the whole contract, and since 2026-08-20 it is the *only* way the site deploys. **Every** push to `master` runs `.github/workflows/deploy-dashboard.yml` - there is deliberately no `paths:` filter - and it installs deps, builds the production bundle from the `VITE_TEABLE_*` **repo secrets** (failing closed if any is missing), and publishes `dashboard/dist` to the `gh-pages` branch (GitHub Pages source: `gh-pages`, path `/`). `workflow_dispatch` redeploys `master` on demand.
  - **No machine is special.** The credentials live in repo secrets, not on a laptop, so a fresh clone with push access can deploy. Nothing needs a local `dashboard/.env`.
  - **There is no local publish path, by design.** `npm run deploy` (the `gh-pages` package) was deleted on 2026-08-20 along with the devDependency. Do not reintroduce it: it published a bundle built from one person's private `.env` and left `gh-pages` out of sync with `master` until the next CI run. Before CI existed it was also the single reason merges sat unpublished (PR #2 merged 2026-07-30, still not live 2026-07-31).
  - **A no-op push is a real run, not a failure.** With the path filter gone, a docs-only push still builds; if the bundle comes out byte-identical the publish step prints "No change in built output, nothing to publish" and exits 0. That costs ~20s and is the point: the old filter's failure mode was a push that missed `dashboard/**`, deployed nothing, and looked like a success.
  - Rotating any `VITE_TEABLE_*` value means updating the repo secret (`gh secret set VITE_TEABLE_TOKEN --repo videoaditor/aditor-scorecard`) as well as local `.env` files.
- **Never sync the publish tree with a heuristic file comparison.** The first CI deploy (2026-07-31) used `rsync -a`, which quick-checks on size+mtime. `index.html` is always the *same byte size* across builds (Vite asset hashes are fixed-length), and that run's build and gh-pages clone landed in the same whole second, so rsync skipped it: the new hashed assets shipped alongside an `index.html` still pointing at the deleted old ones, and `score.aditor.ai` served a blank page from a green run. The workflow now empties the publish tree and copies `dist` fresh, and an integrity gate resolves every local path `index.html` references against the tree before committing. The hashed-asset layout defeats size/mtime comparison by construction - if you touch the publish step, keep both guards.
- **`npm run lint` is currently broken and deliberately excluded from the baseline.** There is no `eslint.config.js` and ESLint 9 requires one (`eslint-plugin-react-hooks` / `eslint-plugin-react-refresh` are already in devDeps; a flat config was intended but is missing). Lint is not in `commands.test`. There is no TypeScript, so "typecheck" is the Vite build. Adding the flat config is optional cleanup, not gate-blocking.
- **Security note (not a test gate).** `VITE_TEABLE_TOKEN` is inlined into the client bundle (`useScorecard.js:3-4`, sent as Bearer at `:93`) and shipped to `score.aditor.ai`, so anyone who loads the dashboard can read it from the JS. No frontend test can cover this. Since 2026-07-31 it is also a repo secret (CI needs it at build time), which does not change the exposure: the bundle is the exposure. Two mitigations verified 2026-07-31: `score.aditor.ai` is behind **Cloudflare Access** (unauthenticated requests 302 to `videoaditor.cloudflareaccess.com`, so the bundle is not internet-readable), and the token is **narrowly scoped** (403s on `/api/auth/user/me` and `/api/access-token`, 200 on the scorecard table read). Its write scope is still **unconfirmed** - nobody has verified it cannot PATCH the table. Confirm that, or move the Teable read behind a backend.
